# 「ノイズから当てる文章ゲーム」開発計画書(仮題)

## 0. この文書の見方

この文書は、これまでの検討内容をまとめた計画書です。各項目には、確度を示すラベルを付けています。

| ラベル | 意味 |
|---|---|
| **【確定】** | 企画者が明示的に決めた内容 |
| **【現行案】** | 検討の中で提案され、仮に採用している内容。試作で見直す余地がある |

## 1. ゲーム概要

### 1.1 一文での説明

3人1組で遊ぶスマホゲームです。各プレイヤーが「主語・目的語・述語」のいずれか1語を入力すると、それが1つの文になり、画像生成モデルがその文を描きます。ノイズから画像が浮かび上がる過程を見ながら、**他の2人が入れた語を選択肢から当てる**早押しゲームです。

### 1.2 面白さの核

- 全員が自分の語だけは知っていて、残り2語を推理する対称な構造になっている。
- 「ノイズから何かが浮かび上がる」過程そのものが観戦して楽しい。
- 選択式の早押しなので、入力速度や語彙力に勝敗が左右されにくい。

### 1.3 設計上の要点(検討で確認したこと)

- 「4人の語を1枚に融合する」方式は、視覚的に強い語だけが支配的になりやすいため採らず、**3語で1文を作り、その文を描く**方式にした。
- 補語のスロットは、描画が難しいため廃止した。
- 出題者に得点を与える方式は、定番語(「ネコ」など)を入れるのが最適戦略になるため廃止した。

## 2. ゲームルール

### 2.1 用語と基本構成

用語は、次の3階層です【現行案。読みが合っているか要確認】。

| 用語 | 意味 |
|---|---|
| **ゲーム** | 1回のプレイ全体。開始時に、ラウンド数を1〜5から指定する |
| **ラウンド** | 3ポイント先取で決着する1試合。最短3ターン、毎ターン得点が入れば最長7ターン、最大10ターン |
| **ターン** | 1問。入力、生成、回答、結果表示までの1サイクル |

基本構成は次の通りです【確定】。

| 項目 | 内容 |
|---|---|
| 人数 | 1グループ3人 |
| スロット | 主語(だれが)、目的語(なにを)、述語(どうした)の3つ。補語は使わない |
| ラウンド数 | 1ゲームあたり1〜5 |
| ラウンドの勝利条件 | 3ポイントを先に取った人がそのラウンドの勝者 |
| ポイントの取り方 | ターンごとに、最も早く正解した人に1点 |
| 最終順位 | ラウンドの勝利数が最も多い人が優勝 |

### 2.2 1ターンの流れ【確定】

| 順番 | 内容 | 時間 |
|---|---|---|
| 1 | 入力。3人が自分の担当スロットに1語を自由入力する | **30秒**(全員が入力したら即終了)【確定 2026-10-16に10秒から変更】 |
| 2 | 翻訳、画像生成、選択肢(ダミー)の生成 | 目標**8秒**以内【現行案 2026-10-18に5秒から変更】 |
| 3 | 事前チェック(画像に3語が描かれているか)※現在は記録のみ | 手順2と合わせて8秒以内【現行案】 |
| 4 | 回答。ノイズから浮かび上がる画像を見ながら答える | 10秒 |
| 5 | 結果表示(正解、得点)。次の問題へ | 5秒前後【現行案】 |

1ターンの所要時間は約53秒です(入力30 + 準備8 + 回答10 + 結果5)。
1ラウンドは3〜10ターンなので約2.7分〜9分、1ゲームは1〜5ラウンドなので約2.7分〜45分が目安です
(5ラウンドで全て最短なら約13分)。

入力を10秒から30秒に変えた理由は、**何を出題するか考えるのに10秒では足りない**ため
【確定 2026-10-16】。全員が入力すれば即終了する仕様なので、決まっている人の待ち時間は増えません。
ただし**1ゲームが最長42分**になるため、ラウンド数の既定値は見直す余地があります【要検証】。

### 2.3 入力のルール

- 入力は自由入力で、サジェストは出さない【確定】。
- 入力時に「この語は絵にしにくいかもしれません」という警告だけを表示する。入力は弾かない【確定】。
- 入力欄には、スロットのラベル(「だれが」「なにを」「どうした」)を表示する【現行案】。
- 同じ語は、**同一ラウンド内**で再利用できない【確定】。
- 担当スロットは、ターンごとにローテーションする【現行案】。全員が全スロットを担当する。
- 不適切な入力(性的、差別的な内容など)には、入力側のフィルタと、出力画像のセーフティチェックの両方をかける【現行案】。

### 2.4 入力の時間切れ

- 制限時間(30秒)以内に入力できなかった人の語は、システムが適当に選んで補う(過去の入力プールから同カテゴリの語を引く)【確定】。
- ペナルティとして、時間切れの人には、そのターンの画像と選択肢が表示されない。そのターンは回答できない【確定。「表示されない」の範囲は、画像と選択肢という読みで仮置き】。
- 2人以上が時間切れなら、そのターンは無効にしてやり直す【確定】。
- 無効になったターンは、ターン数(最大10)に数えない【現行案】。

### 2.5 回答のルール

- 回答は選択式で、選ぶのは**自分以外の2人の語**(2スロット分)【確定】。
- 各スロットは4択。内訳は、正解1、近いダミー1、中くらいのダミー1、遠いダミー1【現行案】。
- 誤答した人は、その問題の解答権を失う【確定】。
- 全員が誤答または時間切れの場合は、無得点で正解を見せて次に進む【現行案】。
- 誤答で2人が失格し、1人だけ残った場合は、そのターンをその1人で最後まで続行する【確定】。残った人は、競争相手がいないので、確信が持てるまで待って答えられる。
- 提出の形式は「2スロットを両方選んで送信し、両方正解で1点」とする【現行案。要確認】。
- 5.5秒にヒントを出す【確定(タイミング)】。ヒントの中身は、各スロットの中くらいのダミーを1つグレーアウトする案【現行案】。
- 選択肢の位置は10秒間固定し、消える選択肢は詰めずにグレーアウトにする(位置が動くとタップが遅れるため)【現行案】。

### 2.6 選択肢(ダミー)の作り方【現行案】

- ダミーは正解と同じカテゴリの語にする(「だれが」の候補に動詞を混ぜない)。
- 正解との埋め込み距離が「近すぎず遠すぎない」範囲で選ぶ。この距離の範囲が難易度のつまみになる。
- 正解にもなりうる語(犬に対する子犬など)は避ける。
- 主語と目的語の選択肢に、同じ語を並べない。
- 供給元は2つを併用する。序盤は、LLMや埋め込み近傍からその場で生成する。使うほど、過去のプレイヤーが入力した語のプールから引く割合を増やす。

### 2.7 ラウンドとゲームの終わり方

- **最終順位**: ゲーム全体で、ラウンドの勝利数が最も多い人が優勝する【確定】。勝利数が同数なら、全ラウンドの合計得点で決め、それも同じなら同率とする【現行案】。
- **1ラウンドの最大ターン数は10**【確定】。この数字は、毎ターン得点が入った場合の最長7ターンに、誰も答えられない(無得点の)ターン3回分を足したものです。無得点のターンが3回以内なら、10ターン以内に必ず決着します。3人で得点が入るターンが7回あれば、誰かが3点に届くためです。
- **10ターンで決着しない場合**(無得点のターンが4回以上あり、得点が2-2-2のように割れたとき)は、最多得点者を勝者とし、同点なら勝者なしの引き分けとする【現行案】。

## 3. 画像生成の仕様

### 3.1 使用モデル

**使用モデルは Z-Image-Turbo(Alibaba / Tongyi-MAI)に決定しました**【確定】。

Z-Image-Turbo の特徴は、次の通りです(報告値)。

- 6Bパラメータの S3-DiT(テキスト、画像の意味、画像VAEのトークンを1本の列で処理する構造)。
- Decoupled-DMD と DMDR(DMDに強化学習を組み合わせた手法)で蒸留した、8ステップのモデル。CFG不要。
- 公式のサンプルでは `num_inference_steps=9` と指定し、HFモデルカードは実際のモデル評価を**8回**と説明している。ただし diffusers の `ZImagePipeline` で transformer の forward を数えたところ、**NFE は `num_inference_steps` と同数**だった(steps=8 で8回、steps=9 で9回。全解像度で一貫)【実測 2026-10-16、E1】。**取れる x0 予測は8枚に縛られない**。詳細は `experiments/e1_generation_speed/FINDINGS.md`。
- テキストエンコーダは Qwen3(4B)。スケジューラはフローマッチングの Euler。
- 対応言語は英語と中国語(日本語は公式の対応に含まれていない)。
- ライセンスは Apache 2.0で、商用利用を含めて認められている。
- 必要なVRAMは16GB前後(BF16)という報告値だが、**実測のピークは20.4〜22.2GB**(512〜1024px、bf16)【実測 2026-10-16、E1】。48GBのうち残りは約26GB。
- 速度は、RTX 4090で1024×1024を約2.3秒(サードパーティの報告値)。**この環境(RTX 6000 Ada)での実測は1024×1024・8ステップで4.69秒**で、報告値の約2倍【実測 2026-10-16、E1】。ゲームで使う解像度の実測は、512が1.08秒、640が1.80秒、768が2.48秒(いずれも8ステップ)。
- 非蒸留のベースモデル(Z-Image-Base)も公開されている。ステップ数と速度は未確認。

検討したが採用しなかった候補は、次の通りです。

| モデル | 採用しなかった理由 |
|---|---|
| SANA-Sprint | 1〜4ステップで、フレーム数が最大4枚になるため、1秒ごとの表示の設計と合わない |
| FLUX.1-schnell | 4ステップで、同じくフレーム数が足りない |
| Krea-2-Turbo | 8ステップだが、ライセンスが Krea 2 Community License で、条件の確認が必要 |

次の問題が出た場合だけ、モデルを再検討します【要検証】。

- E1: 生成時間が、手順2〜3の予算(8秒。当初5秒)に収まらない。
- E1: 序盤の推定画像がすでに鮮明すぎて、「浮かび上がる」変化にならない(DMD系の蒸留の影響があり得る)。この場合は、Z-Image-Base も試す。
- E2、E3: 主語と目的語の役割、3語の判別が、ゲームとして成立しないほど崩れる。

### 3.2 フレームの作り方【確定 2026-10-16: 線形補間】

**最終画像と固定ノイズを画素空間で線形補間してフレームを作る。**
`frame(α) = final × α + noise × (1-α)`。生成するのは最終画像1枚だけで、
途中のステップには一切触らない。

#### α の配り方【現行案】

表示は0〜7秒を**1秒刻みで8フレーム**(§3.3)。切り替えが5.0秒と6.0秒になるので、
5.5秒のヒントが両隣から最も離れる。

α は、時間に対して**後半で一気に鮮明になる**ように配る。

    α(i) = α0 + (1 - α0) × (i / 7)^γ      (i = 0..7)

| つまみ | 現行値 | 意味 |
|---|---|---|
| `α0` | 0.15 | 最初のフレームの鮮明さ。**0にしない**(純ノイズにしない、§3.3) |
| `γ` | 2.0 | 大きいほど、鮮明になるのが遅れて難しくなる。**難易度の主要なつまみ** |

実測の目安は、α=0.17 でかすかに輪郭、α=0.33 で判別可能、0.50以上ではっきり。
γ=2.0 だと判別可能(α≈0.33)に届くのが t≈3秒あたりで、正答を4〜7秒に集めたい
(M6の目安)なら、**γ を上げる方向で調整する**。確定はE7の実測後。

#### なぜこの方式か(M1の結果)

当初案は「各ステップの x0 予測(推定画像)を順番に見せる」だったが、**実測で否定された**。
Z-Image-Turbo は蒸留モデルで、**最初の x0 予測の時点で何が描かれているか判別できてしまう**
(CLIP類似度が step0 で 0.70〜0.86)。シグマ列が `linspace(1, 1/n, n)` で step0 は必ず
σ=1 からの一発推定なので、**ステップ数を増やしても最初のフレームは曖昧にならない**。
非蒸留の Z-Image-Base は 28〜50ステップ・CFG要で概算8秒以上となり予算外。
詳細は `experiments/m1_x0_frames/FINDINGS.md`。

線形補間の利点は3つ。

- **α の配り方がそのまま難易度のつまみ**になる(E7)。
- **枚数が NFE に縛られない**ので、表示タイミングを自由に組める。
- x0 の保存もステップごとのVAEデコード(8枚で約0.3秒)も不要で、**実装も時間も節約できる**。

#### 残っている検証【要検証】

- ノイズの作り方(粒の大きさ、色の有無)は仮。見え方が変わるのでE6で数種類を比べる。
- α の配り方が「推理しやすく楽しい」かはE6・E7で確かめる。

#### 記録: 否定された当初案(x0予測)

以下は実測で否定された手順。再提案を防ぐために残す。


1. 画像生成の各ステップで、そのステップ時点の**最終画像の推定(x0予測)**を保存する。途中の潜在変数をそのままデコードすると、序盤はほぼノイズのままなので使わない。
2. 各ステップの推定画像と、最終画像との類似度(LPIPSまたはCLIP類似度)を測る。
3. 類似度の曲線を、見せたい枚数(6〜7枚が目安)で等間隔に区切り、各区切りに最も近いステップをフレームとして選ぶ。序盤の色の塊や、終盤のほぼ同じ画像は間引かれる。
4. 文ごとに選び直すか、全体の平均で固定するかは、ばらつきを見て決める【要検証】。テンポの安定のため、固定のほうが扱いやすい見込み。(M1実測: 6文すべてで選択が `[0,1,2,3,4,5,7]` と一致した。ただし8ステップから7枚選ぶため、そもそも選ぶ意味が薄い)

注意点として、取れる推定画像の枚数は `num_inference_steps` と同数です(当初は「最大8枚」と書いていましたが、実測で否定されました。§3.1参照)。512pxなら1ステップ0.144秒なので、ステップを増やして枚数を稼ぐ余地はあります。ただし Z-Image-Turbo は8ステップ前後に蒸留されたモデルなので、増やして品質が保たれるかは未検証です【要検証】。また、DMD系の蒸留モデルは、少ないステップで最終画像の分布に合わせるように訓練されているため、序盤のステップでもすでに鮮明な画像が出る可能性があります(推測で、このモデルでは未確認)。「ぼんやりから徐々に鮮明に」という変化が小さい場合は、§3.3の線形補間を使うか、Z-Image-Base を試す【要検証】。

### 3.3 表示のタイミング【現行案】

| 経過時間 | 画面の変化 |
|---|---|
| 0秒 | 最初のフレーム。色や大まかな配置が見える状態にする(純ノイズにしない) |
| 0〜7秒 | 選んだフレームを均等な間隔で切り替える。最後のフレームは7秒以内に出す |
| 5.5秒 | ヒントを出す(フレームの切り替えと重ならないよう、ずらす) |
| 7〜10秒 | 最後のフレームを見てタップする時間 |
| 10秒 | 時間切れ |

- 最終フレームを9〜10秒に出しても、見てからタップする時間が残らないため、7秒までに出す。
- **線形補間で確定**【確定 2026-10-16】。フレームの作り方と α の配り方は §3.2 を参照。
  表示は0〜7秒を1秒刻みで8フレーム。切り替えが5.0秒と6.0秒になり、5.5秒のヒントと重ならない。

### 3.4 事前チェック【現行案】

出題の前に、次の手順で画像を検証する。

1. CLIPのゼロショット分類で、3語それぞれが「候補語の中で上位に来るか」を確認する。
   **候補集合は、実際にプレイヤーに出す4択をそのまま使う**【確定 2026-10-16、E3】。
   CLIPが4択から正解を選べないなら、プレイヤーにも選べない見込みが高い。
   また、**判定は必ず「入力された語そのもの」で行う**。「ヒロオウミヘビ」で出た絵は
   ただのヘビだったが、候補語に「ヘビ」を使えば通ってしまう。
   通過条件は「4択で正解が1位」(マージン閾値は0から始める)【現行案、E7で調整】。
2. 述語(動詞)はCLIPが苦手なので、VLMに尋ねる。**自由記述で「何をしていますか」と聞かず、
   動詞の4択から選ばせる**【確定 2026-10-16、E5】。対照条件(別の文の画像に同じ4択)で
   当て推量ちょうど(25%)に落ちたので、VLMは画像を読んでいる。検証条件での正解率は89%。
   **自由記述の問いは常識で答えられてしまう**(M2のE2で実証済み)。
3. 通らない語があれば、その語をシステムが補完した別の語に差し替えて、再生成する【確定】。
   ただし**差し替えの対象は主語と目的語だけ**とし、述語の判定は記録のみに使う
   【現行案 2026-10-16】。3スロット全部を条件にすると通過率が79%まで落ち、
   5問に1問で差し替えが起きるため(詳細は RULES.md §6)。補完する語は、過去に事前チェックを通った語のプールから、同カテゴリのものを引く【現行案】。
4. 差し替えのやり直しは1回までとし、それでも通らなければ、そのターンを無効にしてやり直す【現行案】。待ち時間の予算(8秒)に収まらない場合は、この上限を見直す。※2026-10-18時点で差し替え自体を無効にしている(RULES.md §6)。
5. 語が差し替えられた人には、ゲーム中の3回目までは何も起きない。4回目以降は減点する【回数は確定。減点の大きさは、そのラウンドの得点から1点(0未満にはしない)という現行案】。
6. 待ち時間が予算を超えそうな場合は、VLMチェックを省略する経路を用意する。

この事前チェックがないと、「絵に出ない語を入れた人が有利になる」ゲームになるため、**必須の仕組み**として扱う(得点が「最初に正解した人」だけに入る設計では、絵に出ない語を入れた人は、自分の語を当てられる心配がないまま、残り2語を当てれば先着できるため)。

### 3.5 日本語の扱い【要検証】

- 入力語を英訳して1文に整形してモデルに渡す【確定】。実装は `server/translate.py`。
  **事前チェックのVLM(Qwen3-VL-8B)を画像なしで使い回す**ので、VRAMの追加はゼロ。
  **実測0.74〜1.11秒**(中央値0.84秒)【実測 2026-10-16】。
- 同音異義語は他の2語の文脈で解く。実測では橋/箸、紙/神の3組とも正解した。
  **壊れた助詞も直る**(「ロボットが植木を水をやる」→ "A robot is watering a tree.")。
- **モデルが知らない語はローマ字に落ちる**(「ツチノコ」→ "a Tsuchinoko"、
  「ヒロオウミヘビ」→ "a Hiro oumi snake")【実測 2026-10-16】。訳せた形にはなるので、
  「訳せない」という信号では弾けない。**絵になるかどうかの判断は事前チェックに委ねる**。
  また、知らない語を誤訳することがある(「将棋の駒」→ "a go piece" は囲碁の石で誤り)【要検証】。
- **文化固有の語は、視覚的な説明に展開させる**【確定 2026-10-18】。プレイテストで
  「鬼が金棒を振り回す」が**おばけが金色の棒を振る絵**になった。原因は生成ではなく翻訳で、
  鬼 → "a ghost"、金棒 → "a gold rod"(金+棒の逐語訳)と訳されていた。
  **モデルは描ける**: 「日本の鬼、赤い肌、角、虎皮の腰巻き、棘のある金棒」と具体的に渡せば
  正しい鬼が出る。翻訳の指示に「逐語訳しない」「日本固有のものは名前を残して短い外見の説明を足す」
  を入れて解決した。検証では 侍/刀→katana、天狗→"bird-headed demon with a long nose"、
  座布団→"a thick cushioned mat" と展開され、普通の語(犬・りんご)は変わらなかった。
  翻訳時間は 0.84秒 → 中央値1.22秒に増えたが、1ターンの準備は約2.4秒で予算内。
- **ダミーは、形が揃わないスロットだけ LLM に作らせる**【確定 2026-10-18】。
  プールは裸の名詞しかないので、「公園で」が来ると
  `['橋', '公園で', 'ラーメン', '自転車']` となり**正解だけ形が違って一目で分かった**。
  翻訳と同じ呼び出しで、同じ文法の形のダミーを3つ返させる(追加のモデル呼び出しなし)。
  実測では「胃袋を出して」に対し `['歯を出して', '目を出して', '手を出して']`、
  「トイレでスマホを」に対し `['公園で花を', '部屋で本を', '車で鍵を']` が返った。
  裸の名詞のスロットは従来どおり語のプールから引く。
  **代償は時間**で、1ターンの準備は中央値5.24秒・最大7.33秒。これを受けて
  **予算を5秒から8秒に改めた**【確定 2026-10-18】。超過分はほぼ翻訳で、
  削れるのは品質(ダミーの形、プロンプトの具体性)だけだったため、数字を実態に合わせた。
- **目的語は「〜を」とは限らない**【確定 2026-10-18】。プレイヤーは「針で」「公園で」
  「腸をだしながら」のように助詞つきや節の形でも入力する。助詞を機械的に貼ると
  「バナナでを切腹する」のように壊れるので、**日本語の文もLLMに組み立てさせる**
  (`sentence_ja`)。述語も名詞で来ることがある(「切腹」)ので、その欄にあるものを
  動作として扱わせる。
- **道具が目的語なら、それ以外の道具を描かせない**【確定 2026-10-18】。
  「侍がバナナで切腹」でバナナとは別に包丁が出た。英文に
  「バナナが唯一の道具、刀や他の武器は写さない」と明示させて解決した。
- **動詞は「体が何をしているか」で書かせる**【確定 2026-10-18】。プレイテストで
  「侍がバナナで切腹する」が**正座してバナナを持っているだけ**、「子供たちが時計を押す」が
  **1人が時計に張り付いている**絵になった。動詞を名前で渡すと、モデルは動作を無視して
  「ありそうな静止画」に逃げる。
  「両手でバナナを握って腹に突き立てる、頭を垂れた切腹の姿勢」のように**姿勢で書くと出る**。
  あわせて「目的語を必ず見える形で別々に描く」「複数は複数のまま」
  「ありえない組み合わせも和らげずそのまま描く」を指示に入れた。
  CFGを上げる案は実測で否定(8ステップCFG3・16ステップとも改善せず、16ステップCFG3は
  絵柄が崩れて予算超過)。**原因は推論設定ではなくプロンプトだった**。
  1ターンの準備は中央値2.79秒・最大3.28秒で予算内。
- **英訳を前提にする**【確定 2026-10-16、E4の実測による】。日本語直入力でも絵は出て、
  同音異義語(橋/箸、紙/神)も文脈から正しく解決されたが、すべての指標で英訳に劣る。
  主語・目的語の出現率は 89% 対 96%、**画像に日本語の文字が描き込まれる失敗が 21% 対 11%**。
  Z-Image は文字描画を売りにしたモデルなので、日本語の文字列を「描くべき文字」と
  解釈してしまう。英訳すればこの経路が断たれる。
  節約できるのは LLM 呼び出し1回分だけ(テキストエンコード自体は0.04秒)なので、
  品質低下に見合わない。詳細は `experiments/m2_japanese_roles/FINDINGS.md`。
- 選択肢の表示は日本語のままにし、内部では英語で照合する構成を想定する。

## 4. システム構成

### 4.1 全体像【現行案】

- **クライアント**: スマホのブラウザで動くWebアプリ。
- **サーバー**: FastAPI と WebSocket で、3人の入力の集約、生成の進行管理、得点計算、画像とヒントの配信を行う。
- **GPUサーバー**: 画像生成、CLIPによる事前チェック、VLMによる動詞チェック、ダミー生成用のLLMを実行する。

### 4.2 使用GPU

**RTX 6000 Ada(VRAM 48GB)**を使います。

- **実測のピークVRAMは36.3GB**(Z-Image-Turbo + Qwen3-VL-8B + CLIP を1プロセスに同居させた状態)
  【実測 2026-10-16】。48GBに対して残りは約11GB。
  **翻訳用のLLMは別途載せず、事前チェックのVLM(Qwen3-VL)を画像なしで使い回す**ことにした
  【確定 2026-10-16】。別のLLMを載せる余地は小さい。
- RTX 4090と同じAda世代なので、近い性能になる見込み。ただし、上の「4090で約2.3秒」は報告値であり、**この環境での速度は実測が必要**【要検証】。
- 画像生成、CLIP、VLM、LLMを同じGPUで並行して動かすと、互いに遅くなる可能性がある【要検証】。重い順に、画像生成を最優先にして、動詞のVLMチェックには時間の上限を設ける。
- **解像度は512×512に決定**【確定 2026-10-16】。スピード重視という企画者の判断による。実測で512は1.08秒、768は2.48秒(8ステップ)。ただし下げるほど絵の細部が潰れるため、**E3で512での事前チェック通過率を必ず測る**。通過率が低ければ、やり直しが増えて結局遅くなるので、その時点で報告して判断を仰ぐ【要検証】。
- 1台のGPUで同時に処理できる生成は限られる。複数グループが同時に遊ぶ場合は、生成が順番待ちになる。試作では、1グループずつの利用を前提にする【現行案】。

### 4.3 同期と配信【現行案】

- 画像は、8〜9枚をすべて先に生成し、事前チェックを通してから配信する(生成しながら1枚ずつ配信すると、事前チェックができない)。
- 選んだフレームを全員のスマホに**先読み**させる。
- 「回答開始の時刻」をサーバー時刻で全員に伝え、各端末はその時刻に合わせて、フレームの切り替えとヒントを行う。通信の遅い人だけ画像が遅れる、という不公平を防ぐ。
- 正誤と先着の判定は、サーバー側で受信時刻を基準に行う。

### 4.4 1問あたりの時間の予算(目標)

| 工程 | 目標 | 備考 |
|---|---|---|
| 入力 | 30秒 | 全員が入力したら即終了 |
| 英訳、画像生成、ダミー生成、事前チェック | 5秒以内 | **実測1.95〜2.33秒**(512px、暖機後)【実測 2026-10-16】。内訳は翻訳0.74〜1.11秒 + 生成1.07〜1.10秒 + 事前チェック0.10〜0.13秒。予算内。ただし**暖機しないと1問目が40秒**かかる(生成の初回24.3秒、翻訳の初回15.1秒)。サーバー起動時に暖機する |
| 回答 | 10秒 | ヒントは5.5秒 |
| 結果表示 | 5秒前後 | |

## 6. 検証計画

ルールをどれだけ磨いても、モデルが「だれが何をどうした」を描けなければ成立しないため、**M2までの検証を最優先**にします。

| ID | 目的 | 方法 | 判断 |
|---|---|---|---|
| E1 | 生成速度と中間フレームの確認 | 8回のモデル評価で生成し、解像度別に時間を測る。各ステップの推定画像も保存する | 手順2〜3の予算(5秒)に収まるか。序盤の推定画像が、すでに鮮明すぎないか(蒸留の影響) |
| E2 | 主語と目的語の役割の再現 | 同じ語のペアで、主語と目的語を入れ替えた2文を20〜30組ずつ生成し、VLMまたは人間が区別できる割合を見る | 高ければ対策なし。低ければ、入れ替えた回答も正解にする。**2026-10-16: 13組を生成済み。VLM判定は2方式とも対照条件で無効と判明したため、人の目での判定待ち**(`experiments/m2_japanese_roles/results/*/E2_review.png`) |
| E3 | 3語の判別 | 生成画像に対し、CLIPのゼロショットで3語が上位に来るかを数える。実際にプレイヤーが入れそうな語で行う | **2026-10-16完了**: 512pxで4択の正解率は主語89%・目的語100%。閾値はマージン0から始める。上げると差し替えが増えて減点が頻発する |
| E4 | 日本語の扱い | 日本語直入力と英訳で、同じ文を生成して比べる。英訳結果もログに残す | 直入力で足りるか。破綻の原因が英訳か、モデルかの切り分け |
| E5 | 動詞の描画 | 述語スロットの成績を単独で集計する(VLMによる確認を含む) | **2026-10-16完了**: 動詞4択で検証89%・対照25%(当て推量と一致)。VLMは画像を読んでおり、**自由入力の述語を許してよい**。E2と違って成立したのは、問いが常識で答えられないため |
| E6 | フレームの見せ方 | 推定画像の系列と、線形補間の系列を、数人に見比べてもらう | どちらが推理しやすく、楽しいか |
| E7 | 難易度 | プレイテストで、正答までの時間の分布を取る。ダミーの近さ、フレームの曖昧さを別々に動かす | 「全員が3秒以内に答える」なら易しすぎ、「誰も10秒で答えられない」なら難しすぎ |

類似度の曲線(E1、M1)は、人間が語を判別できる早さの代用品でしかありません。曲線を出したあと、数人に「何フレーム目で、何の語か分かったか」を答えてもらい、両者がずれていれば、フレームの選び方を人間の判別に合わせて直してください。

## 7. リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| 絵に出ない語の入力 | 絵に出ない語を入れる人が有利になる | 事前チェックを必須にし、通らない問題は無効にする。入力時に警告を出す |
| 役割の取り違え | 「犬が猫を追う」を、猫が犬を追う絵に描く | E2で実測する。低ければ入れ替えた回答も正解にする |
| 動詞の描画失敗 | CLIPは動作の判別が苦手で、動詞の確認が難しい | VLMで確認する。時間の上限を設け、超えたら省略する |
| 事前チェックの誤判定 | 描けているのに不合格とされ、入力者が減点される。動詞は判定が特に誤りやすく、述語の担当者だけ不利になる恐れがある | 3回目まで減点なしにしている。動詞の判定の閾値は、E5の結果を見て決める |
| 生成待ちが長い | 入力後に画面を見つめる時間が続くとテンポが崩れる | 予算(5秒)を設け、再生成は1回まで。待ち時間に演出を入れる |
| GPUの競合 | 同じGPUで複数の処理が並行し、互いに遅くなる | 画像生成を優先する。並行数を計測して調整する |
| 通信の遅延による不公平 | 遅い端末の人だけ不利になる | サーバー時刻での同期と先読み。判定はサーバー側で受信時刻を基準にする |
| ダミーが弱い | 消去法で解ける | 「近すぎず遠すぎない」距離の範囲を守り、近いダミーを1つ入れる |
| 難しすぎる語やマニアックな語 | 誰も答えられない | 入力時の警告と、事前チェックで対応する。**実例(2026-10-16)**: 「ヒロオウミヘビ」は日本語だとただのヘビになり、学名を渡すと足と嘴のある別の生き物を捏造した。**事前チェックは入力語そのもので判定しないと素通りする**(絵は「ヘビ」としては立派なため) |
| CLIPが目立つ対象に引っ張られる | 主語と目的語が1枚に写るため、目立たない側の語が潰される。「男性が犬を洗う」でプール1位が犬になり、主語は20位だった | E3で実測済み(主語89%・目的語100%)。現時点では主語が当てにくい事実を受け入れる。領域を切り出して照合する案は未検証【要検証】 |
| 不適切な入力 | NSFWや差別的な内容 | 入力フィルタと、出力側のセーフティチェック |
| 同時利用による順番待ち | 1台のGPUでは、複数グループの生成が詰まる | 試作では1グループずつ利用する |
| 動詞の語彙の枯渇 | 語の再利用禁止で、動詞が足りなくなる | 禁止範囲を同一ラウンド内に限る(確定済み) |

## 付録: 用語

- **フローマッチング**: ノイズから画像への速度場を学習し、その軌道を積分して画像を作る生成手法。
- **NFE(関数評価回数)**: 画像1枚を作るためにモデルを呼ぶ回数。ステップ数とほぼ同じ意味。
- **x0予測(推定画像)**: 各ステップの時点で、「最終的にこうなるだろう」とモデルが推定した画像。ゲームでは、これを順番に見せる。
- **CLIPゼロショット分類**: 画像と複数の候補語の類似度を比べ、最も近い語を答えさせる方法。
- **VLM**: 画像と文章を同時に扱えるモデル。ここでは、動詞の一致確認に使う。
